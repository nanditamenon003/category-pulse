# Category Pulse

**An AI assistant for a clothing store's floor team.** It watches every product category against its monthly sales target, spots what's genuinely falling behind, works out *why*, and says what to do about it while there's still time to act.

> **All data in this project is simulated.** No real store, sales or customer data is included in the repository. The store model (lines, categories, monthly targets, size ranges) is based on how a real premium apparel store runs, but every number is generated by `src/generate_data.py` from a fixed random seed.

**Live demo:** [category-pulse.streamlit.app](https://category-pulse.streamlit.app/) · **Case study:** [CASE_STUDY.md](CASE_STUDY.md)

## The problem

In many stores, each category (polos, chinos, women's knit tops, kids' denim...) has a monthly unit target. Progress is checked by downloading a sales report from the store's POS/ERP system into a spreadsheet, usually at the end of the day. That process has blind spots:

- **Problems are seen too late.** By the time the numbers are pulled, the selling day is over.
- **"Balance to do" misleads.** A raw gap to target says nothing about how much of the month is left, so a category that will comfortably finish can look worse than one that's in real trouble.
- **Size problems are invisible.** A category can have plenty of stock overall while the sizes most people wear are gone, so it quietly stops selling and nobody notices.
- **Manual spreadsheets break silently.** A formula range that misses a few rows gives wrong totals without any warning.
- **The "why" and "what now" are left to guesswork**: was it fewer shoppers, an empty shelf, missing sizes? Who should staff which floor tomorrow? What should associates offer at the till?

Category Pulse is a layer on top of the store's existing system, not a replacement. It turns the same numbers into timely, explained, actionable signals.

## What it does

| Feature | What the manager sees |
|---|---|
| **Month-to-date pace** | Every category's status in words and colour: Behind, Drifting, On pace, Ahead, or Too early to tell. Includes units per day needed vs actual, and a clearly labelled month-end projection. |
| **Real problems, not noise** | A category is only flagged "behind" if the gap is bigger than normal day-to-day randomness, so small categories don't raise false alarms. |
| **Stock alerts** | Stockouts, **broken size runs** (the shelf looks full but the core sizes are gone), last-piece alerts, and early warnings for sizes likely to run out before the next delivery. |
| **Diagnosis** | For each struggling category: stockout, broken size run, fewer visitors (traffic), or fewer buyers (conversion), with the evidence and one concrete action. |
| **Cross-sell ideas** | Triggered only by real pace deficits, and adapted to the cause (a substitute for a sold-out category, a pairing for the sizes in stock). Targeted by loyalty tier, with the offer that tier responds to. |
| **Staffing** | Tomorrow's peak hours per floor zone, learned from past days of the same kind (weekday vs weekend). |
| **End-of-day summary** | A short plain-English summary to replace the evening spreadsheet: where the month stands, what's behind and why, what to do tomorrow. |
| **AI chat** | Ask anything ("why is womenswear behind — traffic or conversion?"). The AI answers by calling the same tools, and a **"How I got this"** panel shows every lookup and number it used. |
| **Your own data** | Upload a month of your store's figures in an Excel template (or CSV files) and every page switches to your store. See below. |

### Using your own store's data

The **Your data** page has an Excel template with a *Read me* sheet explaining every column, and a sample file (the demo month, filled in).

- **Required:** *Targets* (line, category, monthly target) and *Sales* (date, line, category, units).
- **Optional, each switching on more:** hours, sizes, rupee values and bill counts in *Sales*; a *Stock* sheet (one count is enough, a daily count also shows deliveries); a *Visitors* sheet (per floor, by day or hour); a *Loyalty* sheet (tier level only); and *Settings* (store name, delivery day, sale days).
- Column names are matched loosely (for example "Qty" works for "Units", and day-first dates like 24/05/2026 are read correctly), so an export from the store's own system needs little tidying. CSV files work too, one per sheet.
- Before switching over, the page shows which features the data supports and what would switch the rest on. Anything a page can't show is explained ("Not in your data: stock counts..."), never guessed.
- **Privacy:** uploaded data is read for the visitor's session only and not saved. "Remove my data" clears it. The **AI chat and the tour stay with the demo store**, so uploaded figures are never sent to an AI provider. On the public demo, only upload real company figures with the owner's approval.

### The demo month

The simulation is day 24 of a 31-day month, with four deliberate scenarios. None of them is hard-coded as an outcome: they **emerge from supply events**, because the simulation can only sell what's on the shelf.

| Category | What happens | What Category Pulse finds |
|---|---|---|
| Womens Knit Top | Its day-18 delivery never arrives | Stockout, with shoppers still coming (normal footfall, collapsed buying) and the missed delivery named |
| THM Non Denim Bottom ("chinos") | The warehouse is out of waists 32/34 all month | Broken size run: 60 units on the shelf, none in the sizes most people need |
| LB Knit Top | Sells well above plan | Ahead of pace |
| TJM Denim Bottom, THT Woven Top | Normal trading | On pace |

## Running it

Requires **Python 3.11**.

```bash
git clone https://github.com/nanditamenon003/category-pulse.git
cd category-pulse
python -m venv .venv
```

Activate the environment (Windows: `.venv\Scripts\activate`, macOS/Linux: `source .venv/bin/activate`), then:

```bash
pip install -r requirements.txt
streamlit run src/app.py
```

The dashboard builds its simulated data on first start (or run `python src/generate_data.py` yourself). Everything except the AI chat works with no API key.

**For the AI chat**, copy `.env.example` to `.env` and add a key for the provider set in `src/config.py` (`AI_PROVIDER`):

- `"deepseek"` (current setting) needs `DEEPSEEK_API_KEY`
- `"anthropic"` (Claude, as the original spec intended) needs `ANTHROPIC_API_KEY`

The chat code is the same for both: DeepSeek offers an Anthropic-compatible endpoint, so switching is one line.

Each module can also be run on its own and prints its own checks, e.g. `python src/kpi.py` (pace table and contribution report), `python src/stock.py`, `python src/digest.py` (end-of-day summary), or `python src/agent.py` (terminal chat).

`python tests/test_upload.py` checks that the sample file reads back exactly as the demo store, that loosely named CSV files work, and that broken files are refused with a plain message. `python tests/test_any_store.py` runs the whole engine on a made-up store that looks nothing like the demo (different lines, month and opening hours, stock counted once a day), and on a bare version with only daily sales totals. It checks that planted problems are found and that missing data is reported plainly, not guessed.

### Deploying (Streamlit Community Cloud, free)

1. Sign in at [share.streamlit.io](https://share.streamlit.io) with GitHub and create an app from this repository, with the main file `src/app.py` and Python 3.11.
2. Under **Advanced settings → Secrets**, add `DEEPSEEK_API_KEY = "your-key"`.
3. Deploy. The public demo limits each visitor to a few chat questions (`DEMO_QUESTION_LIMIT` in `src/config.py`), so one visitor can't use up the API credit.

## Design choices in brief

- **Every number comes from the data.** The AI must call tools before answering and may not estimate. Projections are always labelled as projections.
- **Status before numbers.** Green, amber and red are used only for status, always with a word label (so it works for colour-blind users), plus one indigo accent colour for buttons. It's built to be read on a phone.
- **Privacy by design.** Loyalty targeting works at tier level (Platinum, Gold, Silver, Non-member). No individual customer data exists anywhere in the project.
- **No machine-learning model (yet).** With one simulated store, a trained model would only re-learn the simulator's own rules. Simple, explainable projections are used instead. See the case study.

## Limitations

- All data is simulated, for one store, at hourly granularity.
- Footfall is simulated per floor zone; many real stores only count visitors at the door.
- Size ranges are simplified, and projections are simple run-rates.
- Each chat question is answered on its own (no conversation memory). Answers take roughly 5 to 30 seconds while the AI looks things up.
- A real-data pilot would need the store's approval, and an AI provider the company approves.
